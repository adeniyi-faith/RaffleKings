# RaffleKings Overhaul Checklist

This is the build/migrate plan that follows from `../` root's audit artifact
("RaffleKings — Product, Feature, UX & Architecture Audit"). Each item below
is a **full, self-contained pass** — the kind of chunk one person or one
focused session can actually finish and ship — not a tiny incremental diff.
Doing them in order matters less than doing each one completely before
moving on; dependencies are noted where they're real.

Everything here builds on what already exists in `raffle-api/`: the
`Wallet`/`BankAccount` models, the guarded legacy-table migrations, and the
tested `TicketPurchaseService` — see `LEGACY_MIGRATION.md` for what's
already there and the ground rules for touching the shared database.

---

## Phase 4 — Post-launch fix & improve (September 2026 gap audit)

The new site replaced the WordPress site at rafflekings.com.ng (see `.github/workflows/raffle-api-deploy.yml`'s "Archive the old site" step) — the old pages and the old WordPress admin are no longer reachable at all. A full old-vs-new comparison in September 2026 found that several gaps above are therefore live problems, not future cutover work, and that some new pages are less capable than the old ones. The rule for everything below: **every page and feature must be equal to the old site or better — more interactive, more alive — never less.** Phases are ordered by harm: money and trust first, then the tools staff need daily, then customer features and polish.

- [ ] **41. Phase 1 — Get money and logins working on the live site.** The live settings file is rewritten from a fixed template on every deploy, and that template had no lines at all for payment, email, push, Telegram, bot-protection or Gemini keys — so top-ups failed for every customer ("All payment gateways are currently unavailable… missing PAYSTACK_SECRET_KEY", reproduced), email was "log only" (no password-reset codes, receipts or winner notices), nothing ever ran the queue, and admin balance tools credited a store customers can't see.
  - [x] **Admin money always lands where customers can see it.** `UserManagementService::adjustBalance()`, `DepositApprovalService` and `TransactionMonitorService` only used the `wallets`/`user_points` tables when the legacy `rk_wallets_unified_enabled`/`rk_rewards_unified_enabled` switches were on — both default off — otherwise they wrote `wp_usermeta`, which the live site never reads. Now always the new tables. Also fixed along the way: `adjustBalance()` wasn't inside a database transaction (its row lock did nothing, and a failure half-way could apply a balance change without its record), and a subtraction that hit the ₦0 floor recorded the full requested amount in the ledger, so Financial Reconciliation would have flagged a drift that never happened — the ledger now records what was actually applied.
