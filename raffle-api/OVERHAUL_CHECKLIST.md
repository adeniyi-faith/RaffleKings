# RaffleKings Overhaul Checklist

This is the build/migrate plan that follows from `../` root's audit artifact
("RaffleKings — Product, Feature, UX & Architecture Audit"). Each item below
is a **full, self-contained pass** — the kind of chunk one person or one
focused session can actually finish and ship — not a tiny incremental diff.
Doing them in order matters less than doing each one completely before
moving on; dependencies are noted where they're real.

Everything here builds on what already exists in `raffle-api/`: the
`Wallet`/`BankAccount` models, the guarded legacy-table migrations, and the
tested `TicketPurchaseService` — see `LEGACY_MIGRATION.md` for what's
already there and the ground rules for touching the shared database.

---

- [x] **1. Ship the four critical live-site fixes as one reviewed patch set**: rate-limit the password-reset OTP, make `logout.php` actually end the server session, wrap wallet-debit + ticket-insert in a transaction with rollback on collision, and add CSRF protection to every money-moving action in `ajax-router.php`. *(Done — the OTP request and OTP-guess endpoints are both rate-limited separately (`api-auth.php`), `logout.php` now calls the router's `logout` action to end the WordPress session server-side instead of only clearing `localStorage`, the wallet/earnings debit + transaction record + ticket-entry inserts in `rk_handle_payment_ai` are one atomic transaction that rolls back on a ticket-number collision instead of charging with no ticket issued, and `ajax-router.php` now checks Origin/Referer against the site's own host on every non-GET action.)*
- [x] **2. Verify and close the bank-transfer ticket-entry gap (TD-05)** against the live database, and fix the admin deposit-approval queue filter so it actually matches real deposit records (TD-28). *(Done — a bank-transfer ticket purchase now saves its raffle/numbers on the transaction row and actually issues tickets once verified, whether that's the AI check passing instantly or an admin approving it later; a numbers collision falls back to manual review instead of silently losing the ticket. The admin "Pending Deposits" queue filtered on `type = 'deposit_manual'`, a value nothing writes — fixed to match the real `wallet_deposit`/`ticket_purchase` types, with a type badge so admins can tell them apart.)*
- [x] **3. Build a real, working customer support ticketing system** to replace the fake one on `support.php` — this doesn't need to wait for the rewrite and is the single most user-harmful gap in the product today. *(Done — new `raffle_support_tickets`/`raffle_support_messages` tables, real list/view/create/reply endpoints (`api-support.php`), rate-limited and ownership-checked (a ticket that isn't yours 404s like one that doesn't exist), a Telegram alert to admins on every new ticket/reply, and a new admin "Support Tickets" page to actually read and answer them. `support.php` now loads real tickets and submits real ones instead of faking it entirely client-side.)*
- [x] **4. Stand up CI + staging + rollback** for the live PHP app: tests (even a first small set) must pass before a deploy, deploys go through a real pipeline instead of a raw `git pull` to production, and a bad deploy can be reverted in minutes. *(Done — `ci.yml` syntax-checks every PHP file and runs a first PHPUnit suite (`rk_calculate_ticket_price`, the function the checkout price-mismatch guard depends on) on every push/PR; `deploy.yml` gates the real deploy behind that same test job and now tags the server's pre-deploy commit before a `fetch` + `reset --hard` (not a raw `pull`); `rollback.yml` is a manually-triggered workflow to snap back to that tag or any commit; `staging-deploy.yml` runs the same pipeline against a `staging` branch/target once its `CPANEL_STAGING_*` secrets are set.)*
- [x] **5. Add an admin action audit log** (new table + a logging call wired into every mutating admin action in `admin-panel.php`) so every approval, ban, and balance edit is traceable to a person and a time. *(Done — new `raffle_admin_audit_logs` table + `rk_log_admin_action()`, wired into every mutating admin action across Financials, Withdrawals, Transactions, User Manager, Referrals, Site Alerts, Bonus System, Live Comments, Settings, and the new Support Tickets page. New "Admin Audit Log" page under Raffle Ops to read it.)*
- [x] **6. Repository cleanup pass**: delete `currentapi.php`, `oldwithdraw`, `.htaccess.zip`, `.htaccess_bak`, the empty `promo-popup.php`, and the orphaned pages (`category-cash.php`, `category-gadgets.php`, `category-scholarships.php`, `marketing-ui.php`, `view-story.php`) or explicitly wire them up — don't leave dead, confusing code live. *(Done — all ten deleted after confirming nothing in the repo references any of them.)*
- [x] **7. Turn off the two worst trust-damaging dark patterns immediately**: make the spin-to-win popup's odds genuinely match what it displays, and remove every fabricated "X people viewing" / fake activity counter across `index.php`, `raffles.php`, and `checkout.php`. *(Done — the Spin & Win wheel's slices are now drawn proportional to the real 60/30/8/2% server-side odds instead of four equal quarters, the exact percentages are shown under the wheel, and the false "Guaranteed win on every 10th spin!" claim (nothing tracked a spin count) is gone. Removed index.php's fake "Live Activity Ticker" (~80 fabricated usernames + made-up amounts cycling every 3.5s) and its "1,200+ people are playing these" claim, raffles.php's dead random-walk "viewing count", and checkout.php's hardcoded "3 other people are viewing this raffle" exit-modal claim. A real, honest live-activity signal is Phase 2 item 30 — this item was just "turn it off now".)*

## Phase 1 — Laravel backend foundation (`raffle-api/`)

- [x] **8. Build the WordPress-session auth bridge**: a custom Laravel guard that reads the existing `wp_users`/session cookie, so a user's login keeps working identically while both systems run side by side. This unblocks every other Laravel route. *(Done — `app/Auth/WordPressAuthCookieValidator.php`, `app/Auth/WordPressSessionGuard.php`, the `wordpress` guard, and a working `/api/me` proof-of-concept route, all covered by tests.)*
- [x] **9. Wire `TicketPurchaseService` to real controllers and routes**, plus build the raffle-listing and raffle-detail read endpoints (replacing the WordPress CPT read path for the frontend). This is the first real, live Laravel feature. *(Done — `GET /api/raffles`, `GET /api/raffles/{id}` (public, ticket counts always derived from real entries, fixing TD-13), and `POST /api/tickets/purchase` (auth required). Not yet pointed at by the live frontend — see the controller's docblock and Phase 3.)*
- [x] **10. Model raffles and prize structures natively in Laravel**, replacing the WordPress custom-post-type + external ACF field dependency the current draw logic relies on. Include a migration that reads today's raffle/prize data out of WordPress once, correctly, for a one-time cutover. *(Done — `raffles`/`raffle_prize_tiers` tables, `App\Models\Raffle`/`RafflePrizeTier`, and `php artisan legacy:import-raffles [--dry-run]`, which also recovers the undocumented ACF "prize_structure" repeater fields the draw engine silently depends on. Not yet the live read/draw path — see item 12.)*
- [x] **11. Build the real ledger + wallet service**: an append-only debit/credit ledger table with the `wallets` table as a fast-read balance cache derived from it, plus a migration/backfill that reconciles every existing `usermeta` balance into it exactly once. *(Done — `wallet_ledger_entries` table, `App\Models\WalletLedgerEntry`, `App\Services\WalletLedgerService` (`recordDebit`/`recordCredit`/`reconstructBalance`), and `php artisan legacy:reconcile-wallet-ledger [--dry-run]` to give every backfilled wallet an honest opening-balance entry. `TicketPurchaseService` now writes a ledger entry for every debit inside the same atomic transaction as the balance mutation — including the TD-06 rollback path, which now rolls the ledger entry back too.)*
- [x] **12. Build bank account management** (add/remove/set-primary) fully on the new `bank_accounts` table, replacing the serialized-array `usermeta` version. *(Done — `App\Services\BankAccountService` + `BankAccountController`, at `GET/POST /api/bank-accounts`, `PATCH /api/bank-accounts/{id}/primary`, `DELETE /api/bank-accounts/{id}`. Keeps the legacy site's own rules — max 2 accounts, 10-digit Nigerian account numbers, auto-promoting a replacement primary on delete — so behaviour won't change for users at cutover. Also fixed a real bug this work turned up: the WordPress-session guard from item 8 was caching the first resolved user across separate requests sharing one guard instance — safe under classic PHP-FPM, but a real risk under a long-running worker like Octane, and a real bug in tests. Fixed and covered by a regression test.)*
- [x] **13. Integrate a real Nigerian payment gateway** (Paystack or Flutterwave) for deposits, with webhook-confirmed settlement feeding the same `TicketPurchaseService`/ledger path — keep the Gemini AI screenshot check only as a manual-review fallback for edge cases the gateway can't handle. *(Done — Paystack is the default gateway, Flutterwave an automatic backup: `App\Services\DepositService` (the single settlement path, same discipline as `TicketPurchaseService`/`WithdrawalService`) tries Paystack first at `POST /api/deposits` and falls back to Flutterwave only if Paystack's own initialization call fails, e.g. an outage. Once a deposit is created against whichever gateway handled it, only that gateway is ever consulted again for it. Settlement happens at `POST /api/webhooks/{paystack,flutterwave}` — a webhook's signature only proves it came from the gateway, it is never trusted for the actual credit; `DepositService::confirm()` always re-verifies the transaction directly against that gateway's own API before crediting the `wallets` table, and is idempotent (a duplicate webhook, or the gateway retrying, cannot double-credit). A confirmed payment for the wrong amount is flagged `amount_mismatch` rather than credited on a guess. First-deposit referral commissions (item 15) now actually fire, for the first time since that service was built — this was its missing live trigger. The Gemini AI screenshot check is untouched and still available as the manual-review path for anything neither gateway can handle.)*
- [x] **14. Build the provably-fair draw engine**: commit a hashed random seed before ticket sales close, reveal it after the draw, and expose a page/endpoint where anyone can independently recompute the result — this replaces the current cosmetic "verification hash" and the non-cryptographic shuffle. *(Done — `App\Services\ProvablyFairDrawService` (commit/run/verify), `raffle_draws` table, and `GET /api/raffles/{id}/draw` (public commitment + full recomputed verification) plus admin-gated `POST .../draw/commit` and `.../draw/run`. Winners are written to the SAME `wp_raffle_winners` table the legacy draw uses, so Hall of Fame/admin winner tools don't need to change. Added a minimal `isAdministrator()`/`admin` middleware gate along the way — a real role system is still item 19.)*
- [x] **15. Build the referral & commission engine** on the new ledger, fixing the paid/pending status bug found in the audit, and make the commission rate a configurable value rather than hardcoded. *(Done — `App\Services\ReferralCommissionService`, a `referral_commissions` table (one real row per referee, ever — structurally fixes TD-33's meta-key mismatch instead of just patching it), `config/referrals.php` for the rate (defaults to the legacy 50%), and `GET /api/referrals/stats`. Not yet wired to a live trigger — there's no deposit code path in Laravel until item 13 (payment gateway) exists; call it right after a deposit is verified once that's built.)*
- [x] **16. Build the points, daily-streak, and Spin & Win engine** with a cryptographically strong random source and publicly documented odds (turning the existing hidden house edge into a disclosed one). *(Done — `PointsService` (the single settlement path, mirroring `TicketPurchaseService`'s discipline) plus `DailyClaimService`, `TaskClaimService`, `SpinService`, and `PointRedemptionService`, all under `/api/rewards/*`. Spin uses `random_int()` instead of `rand()`, and `GET /api/rewards/spin/odds` is public — the same ~8% house edge as the legacy game, now disclosed rather than hidden. A new `point_ledger_entries` table gives points the same real audit trail as money.)*
- [x] **17. Build the queued notification system**: every email/push/SMS/Telegram send goes through a Redis-backed queue with retries and a dead-letter list for anything that keeps failing, replacing today's silent, unretried, synchronous sends. *(Done — `App\Notifications\Channels\OneSignalChannel`/`TelegramChannel` (queued, real TLS verification, retry-on-failure instead of the legacy's silently-discarded result), wired into two real triggers: `WinnerAnnounced` + `DrawCompletedAdminAlert` from the draw engine, and `TicketPurchaseReceipt` from the purchase flow — both fire only after their DB transaction commits. Retries (3 attempts, backoff) land in Laravel's own `failed_jobs` table as the dead-letter list, no bespoke table needed. Queue driver is `database` for now (zero extra setup); switching to `redis` in production is a one-line env change, not a code change. SMS has no provider chosen yet — same open question as item 13.)*
- [x] **18. Build the withdrawal engine** on the new ledger, including a clear, *upfront-disclosed* version of any account-verification requirement — not one a user discovers only when trying to cash out. *(Done — `App\Services\WithdrawalService` + `withdrawal_requests` table, at `GET /api/withdrawals/requirements` (shows whether the verification fee applies, before a user ever submits) and `POST /api/withdrawals` (rate-limited 3/5min). Same ₦2,000 minimum and ₦1,000 verification-fee mechanic as the legacy site — the fee mechanic itself is a product decision (audit §15), not something silently changed here; what's fixed is that it's now disclosed upfront instead of sprung on the user at cash-out.)*
- [x] **19. Build the admin console** (recommend Filament) covering, as one complete pass: deposits & withdrawals queue, user management, raffle & prize management, winners & payouts, referrals & rewards, financial reconciliation, system health, and the audit log from item 5 — replacing both the WordPress admin panel and the half-built `/admin` rebuild with one real system. *(Done, as a JSON API (`/api/admin/*`) plus a real Filament UI at `/admin`. JSON API: withdrawals queue (list/pay/reject), winner payouts (credit/visibility, fixing the TD-12 double-credit race with a real row lock), support tickets (item 20), and the audit log (`AdminAuditLogService` + `admin_audit_logs`, fixing TD-15). Filament UI (`App\Providers\Filament\AdminPanelProvider`, installed after the earlier proxy-timeout failure turned out to be a stale `vendor/nesbot/carbon` checkout, not a real dependency problem — `rm -rf vendor && composer install` from the already-resolved lock file fixed it): `UserResource` (search/filter users, see each one's wallet + earnings balance at a glance, ban/unban via a new `UserManagementService` that writes the same `rk_is_banned` usermeta the legacy site already reads, every change audit-logged); `RaffleResource` with a prize-tier relation manager (create/edit raffles and their prize tiers natively, replacing the WordPress CPT + ACF repeater editing flow); and a `FinancialReconciliation` page that sums each user's `WalletLedgerEntry` rows and flags any wallet whose stored balance has drifted from what its own ledger says it should be — the honest test of whether every money-moving service in this app is actually staying on its single settlement path. The panel reuses the SAME WordPress session cookie every other part of this app already bridges (`WpUser` now also implements Filament's `FilamentUser`/`HasName` contracts, gated by the same `isAdministrator()` check) — no separate Filament login or password. Getting this working also fixed a latent bug: the WordPress cookie is never Laravel-encrypted, and the framework's default `EncryptCookies` middleware (only relevant once a real 'web'-routed page existed) would have silently stripped it; it's now excepted globally in `bootstrap/app.php`.)*
- [x] **20. Build the support/disputes console** for admins, tied to the ticketing system from item 3, so support requests have a real internal queue and response workflow. *(Done — `support_tickets`/`support_ticket_messages` tables, `App\Services\SupportTicketService` (single settlement path for opening/replying/status changes), user-facing endpoints at `GET/POST /api/support/tickets`, `GET /api/support/tickets/{id}`, `POST /api/support/tickets/{id}/reply` (ownership-checked, returns 404 rather than 403 on someone else's ticket to avoid leaking which ticket IDs exist), and admin endpoints at `GET /api/admin/support/tickets` (paginated, filterable by status), `GET .../{id}`, `POST .../{id}/reply`, `PATCH .../{id}/status` — replies and status changes are recorded in the admin audit log from item 19. An admin reply queues `SupportTicketReply` to the ticket's owner; a new ticket queues `NewSupportTicketAdminAlert`, both through the same queued-notification path as item 17. This closes the single most user-harmful gap the audit found: the legacy "Submit Ticket" button never actually sent anything anywhere.)*

## Phase 2 — Frontend rebuild

- [x] **21. Set up a real frontend build pipeline**: a bundler, pinned dependency versions, no more Tailwind Play CDN or `@latest` icon packages — the site's appearance and behavior can no longer change without a deploy. *(Done — the new frontend is Inertia.js + React + Tailwind, built with Vite, living in `raffle-api/` (the app the rest of Phase 2 builds on; the root PHP pages stay as-is until each one is cut over in items 23-31, then deleted in item 40). `composer require inertiajs/inertia-laravel` + `@inertiajs/react`/`react`/`react-dom` via npm, `HandleInertiaRequests` middleware, an `app.blade.php` root view, and a `resources/js/Pages/` directory for page components — proven end-to-end with a real `GET /` route rendering a `Home` page through the built Vite bundle. All frontend dependency versions in `package.json` are pinned exactly (no `^`/`~` ranges), with `package-lock.json` committed, so `npm install` reproduces the exact same build every time — the same discipline `composer.lock` already gave the PHP side. Dropped a remote Google/Bunny-font fetch that was wired into the build (it would silently fail the entire build with no internet access, e.g. in CI) in favor of a safe local system-font fallback — no build step should depend on reaching the internet to succeed. `raffle-api/.github/workflows/tests.yml` (a stock Laravel starter workflow, never previously customized for this repo) now also runs `npm ci && npm run build` on every push/PR, so a broken frontend build fails CI the same way a broken test does.)*
- [x] **22. Build a shared component library** (buttons, modals, cards, form inputs, price displays) to replace the copy-pasted markup and triple-duplicated pricing math currently spread across `checkout.php`, `raffle-details.php`, and `register-special.php`. *(Done — `resources/js/Components/ui/` (`Button`, `Modal`, `Card`/`SelectableCard`, `TextInput`/`PasswordInput`, `NumberStepper`, `Price`'s `PriceTag`/`DiscountBadge`/`PriceSummaryFooter`) reproduces the real Tailwind markup shared across all three legacy pages — button/modal/card shells that were copy-pasted verbatim, the missing `aria-label` on password-toggle buttons now included by default, and a `SelectableCard` that unifies what were two near-identical "selectable option" patterns (ticket-bundle tiers and payment-method choices). The legacy pricing math itself is the more serious fix: `checkout.php`, `raffle-details.php`, and `register-special.php` each hand-rolled their own copy of `calculateDiscountedPrice()`, and the copies had actually drifted (different rounding, one missing the Golden Box multiplier's return value) — exactly the class of bug `TicketPricingService` (Phase 1 item 9) was already built to prevent, but nothing yet called it from the frontend. New public `GET /api/raffles/{id}/price-quote?quantity=N` endpoint (`TicketPriceQuoteController`) and a `useTicketPriceQuote()` hook replace all client-side recalculation — every price shown in the new frontend now comes from the same server formula that will settle the charge, so display and charge can no longer drift apart. Design tokens (`app-primary`/`app-secondary`/`app-bg`/`dark-*` colors, Inter font, class-based dark mode) that were previously three separately drifting inline `tailwind.config` copies are now defined once in `resources/css/app.css`. A `/dev/components` route (non-production only) renders every component against a real price quote for visual verification — screenshotted in both light and dark mode during development, which caught and fixed a real contrast bug (card text had no dark-mode color set, making it nearly unreadable on the dark background) before it could ship.)*

## Phase 3 — Cutover, hardening, and decommissioning

- [ ] **32. Run a shadow-traffic period**: real ticket-purchase requests are also run (without effect) through the new Laravel settlement path and compared against the old PHP path's output, catching any mismatch before it can affect a real user.
- [ ] **33. Cut over ticket purchase, wallet, and payments to Laravel first** (highest financial risk, and the module already furthest along), with a fast per-module rollback path to the old PHP code if anything misbehaves.
- [ ] **34. Cut over authentication to Laravel-issued tokens (Sanctum)**, retiring the WordPress-session dependency built in item 8.
- [ ] **35. Cut over the draw engine, referrals, rewards, and notifications**, in that order, each validated against its own test suite before going live.
- [ ] **36. Cut over admin operations fully** to the new console from item 19, and formally retire both the WordPress admin panel and the `/admin` placeholder rebuild.
- [ ] **37. Add production monitoring**: error tracking (e.g. Sentry), structured request-traced logging, and a queue-health dashboard (e.g. Horizon) — so incidents are caught automatically instead of discovered from user complaints.
- [ ] **38. Add responsible-participation controls** (self-exclusion, spending limits, clear odds disclosure) before the new system becomes the primary way users interact with the product.
- [ ] **39. Run a full security pass** on the finished Laravel app (CSRF, auth, rate limiting, admin permissions, webhook signature verification) before final public cutover.
- [ ] **40. Decommission the legacy PHP/WordPress codebase** once the Laravel system has run correctly, unmodified, through at least one full billing/reporting cycle — remove the old `wp/` install, the root PHP pages, and the `/admin` folder from the live server and the repository.
